# MoE 专家预取：算法路线、近期进展与端侧适用性

调研截止：2026-09-18。目标场景：手机端 MoE，Flash–DRAM–SRAM 存储层级，batch=1；重点优化 Flash→DRAM 专家加载造成的逐 token decode 等待。本文保留跨平台文献地图，并单独说明对该场景的适用性。

配套设计：[专家激活剪枝与预取协同算法](D:/华为/MoE-Compressors/docs/research/moe_prefetch_pruning_proposals.md)。

## 1. 结论

MoE prefetch 的核心，是在真实 router 给出专家集合之前预测需求，把专家权重搬运与已有计算重叠起来。近年的公开进展已经从“猜下一层专家”走向四项联合决策：**预测谁会用、安排何时搬、决定缓存谁、处理没及时到的专家**。

对本仓库最重要的结论如下：

1. **激活剪枝与预取具有协同空间，而且已有直接先例。** AdapMoE（2024）已经将敏感度驱动的动态专家减少、考虑剪枝的未来需求预测和缓存分配放在一起。“剪枝 + prefetch”本身不足以构成研究创新。
2. **预测命中率不是最终目标，按时到位且确实有用才是。** ProMoE 关注预测与及时到位的共同效果；SpecPrefetch 限制可隐藏的预取量；SeqMoE 将传输组织成带截止时间的调度问题。预测过多会争抢带宽、挤掉有效缓存。
3. **近年的一个重要方向是容忍部分 miss。** BuddyMoE 用已驻留的相似专家替代缺失专家；APEX 提供基于已到位专家的近似模式；SPICE 使用共享专家和低秩残差补偿，并对重要缺失执行精确恢复。这些是剪枝、替换、补偿方案必须对照的工作。
4. **移动端证据需要区分真实硬件与仿真。** SpecPrefetch 有真实 Snapdragon 平台实验，但较大的收益包含模拟慢速 UFS 延迟的实验；APEX 的硬件收益来自综合校准的周期级协同仿真。不能把桌面 PCIe 实验直接解释为手机实测。
5. **建议研究目标：在给定质量和手机 DRAM 预算下，联合选择实际执行专家、Flash 预取集合及 DRAM 缓存策略，减少实际读取和暴露在关键路径上的等待。** 采用“冷专家跳过 + 剪枝后需求预取”，再加入 DRAM 内替换补偿；单独优化平均激活数、cache hit 或 predictor accuracy 都可能偏离这个目标。

### 证据范围

本次覆盖 25 项代表性公开工作，时间跨度为 2023–2026；最近纳入的预印本为 2026-09-11 提交的 SeqMoE。检索围绕 expert prefetch / offloading / prediction / caching / dynamic gating / expert substitution 展开，通过论文原文、arXiv 元数据、作者仓库与论文参考文献交叉追溯。

## 2. 先定位“参数读取”的存储层级

这里将参数 require 理解为专家权重的读取、加载或搬运需求，而非训练时的 requires_grad。

| 场景 | 主要瓶颈 | 预取能做什么 | 激活剪枝能做什么 |
|---|---|---|---|
| CPU DRAM → 独立 GPU 显存 | PCIe 搬运、排队、显存容量 | 提前 H2D，利用 attention / 其他专家计算隐藏传输 | 降低实际需求和传输量，给有价值的预取释放带宽 |
| SSD / UFS → 主存或统一内存 | 存储吞吐、读延迟、页缺失、内存容量 | 异步读、合并读、预先驻留到内存 | 少读取专家文件/块，降低工作集 |
| 权重已在统一 DRAM，计算单元读取到片上缓存 | DRAM 带宽、访问延迟、缓存复用 | 有时隐藏访问延迟、改善局部性，但不能创造带宽 | 直接减少权重读流量和计算 |
| 专家并行，多卡 token 分发 | 网络 all-to-all、负载不均 | 提前安排 token / 通信，与权重预取不同 | 可能减少通信或改变负载，需单独建模 |

本项目采用第二行的 Flash→DRAM 路径。DRAM→SRAM 的访问与计算成本仍计入时间线；第一行的 PCIe 系统用于借鉴预测和调度机制，其传输模型与性能数字不直接用于手机。

### 面向本项目的文献使用方式

| 工作或路线 | 适合借鉴的部分 | 手机实验需要验证的部分 |
|---|---|---|
| HOBBIT、SpecPrefetch | 端侧/慢存储实验、加载预算、计算与读取重叠 | 实际手机 Flash 请求时延、随机/连续读、page cache、内存占用 |
| AdapMoE | 质量敏感度、剪枝感知需求、缓存分配 | 在 Flash 代价模型下重新比较字节和等待收益 |
| ProMoE、SeqMoE | 需求优先、就绪优先执行、预测与截止时间 | 手机文件 I/O 的队列/取消能力、轻量预测器的成本 |
| BuddyMoE、APEX、SPICE | 质量受控的缺失专家替换/补偿 | DRAM-ready 候选的条件误差及额外计算/参数成本 |
| CPU/GPU 异构执行 | 已驻留权重的执行成本比较 | 专家仍在 Flash 时，各计算单元都依赖读取，不能通过改执行位置绕过冷读取 |
| 多 batch 流水、专家并行通信 | 文献背景 | 本项目使用单请求时间线，评价 batch=1 的 TPOT 与 TTFT |

需要特别区分“文件 read”“page-cache 命中”和“真实 Flash 读取”。page cache 属于 DRAM，mmap 映射成功也不等于数据已经到位；内核预读、应用副本和 I/O buffer 都要按实际占用计入内存。

在 batch=1 decode 中，预取窗口来自同一请求的 attention、其他专家或前面层的计算，也可利用历史 token 预测后续需求。同层窗口是否足以覆盖 Flash 读取，需要 profiling 后决定。单请求 prefill 包含多个 prompt token，其缓存起点和 TTFT 单独测量。

对单个专家的简化估算为：

    传输完成所需时间 ≈ 排队时间 + 设置开销 + 剩余字节数 / 有效带宽
    暴露的等待 ≈ max(0, 传输完成所需时间 − 可用计算窗口)

这是局部直觉，不是整个模型的可加时延公式。多个专家通常共享存储/总线和缓存；实际关键路径取决于执行顺序、已有队列、量化解码、DMA 粒度及读写竞争。

在稳定吞吐且相应资源能够并行的简化条件下：

    每 token 时间下界 ≥ max(不可避免的计算时间, 必要权重流量 / 有效带宽)

如果计算也竞争同一内存带宽，这个下界还会偏乐观。预取主要隐藏时间，剪枝和量化才能减少必要字节；二者的作用不能互相替代。

## 3. 常用算法方案

### 3.1 基于热度、局部性和历史轨迹

**信号：** 专家访问频率、上一 token 的激活、同一请求的历史路径、层间共激活。

**流程：** 维护频率或条件转移统计 → 预测近期可能访问的专家 → 异步加载 → 用 LRU、LFU 或轨迹评分进行替换。

**代表：** Fast Inference with Offloading、MoE-Infinity；HybriMoE 将预取优先级进一步与预期收益联系起来。

优点是实现轻、预测状态小；不足是热度不等于当前 token 的真实需求，任务切换和长尾专家容易失配。缓存策略与预取策略需要分开评估：较高缓存命中并不一定来自较准确的未来预测。

适合作为端侧必备低成本基线，也是学习式预测器的 fallback。

### 3.2 用当前 hidden state 提前调用后续层原生 gate

**信号：** 相邻层 residual hidden state 的相关性。

**流程：** 将当前表示输入下一层或后续几层的原生 gate → 取预测候选 → 提前加载 → 到真实 gate 处纠正。

**代表：** Fast Inference with Offloading、AdapMoE、HOBBIT、FATE。

无需另训大型预测器，但跨越 attention / MoE 变换后表示会变化。看得越远，时间窗越长，预测误差也可能越大。HOBBIT 将多个预测 gate 计算组合起来以降低调用开销；FATE 根据概率阈值扩展候选，并配合缓存。

注意三个指标的区别：FATE 报告的基础 decode 预测准确度约 78.79%，扩展候选后约 97.15%，结合缓存后的命中约 99.08%。最后一个数字不等于固定候选预算下的预测准确度，也不能自动推出无等待。

### 3.3 轻量学习式预测：跨层与同层 pre-attention

**信号：** 较早时刻的 hidden state、层号、历史路由及热度特征。

**流程：** 离线采集原生路由标签 → 训练轻量 MLP / 低秩映射 → 在线提前预测分布或排名 → 结合缓存与带宽决定预取集合。

**代表：**

- ProMoE：中间状态预测器、stride prediction，以及围绕异步传输的系统调度。
- Pre-Attention Expert Prediction：使用同层 attention 前的表示预测 attention 后的真实路由，可覆盖第一 MoE 层。
- DuoServe-MoE：decode 使用层相关预测，prefill 则采取不同的流水机制。
- SpecPrefetch：低秩适配器，经原生路由分布蒸馏学习下一层专家预测；同时限制预取预算。
- PreScope：公开摘要描述了层感知学习式预测与跨层调度。

同层 pre-attention 的窗口主要是 attention 计算；跨层预测的窗口更长，但误差累积更明显。预测器开销、特征跨设备复制和所有层预测器总参数量都要计入预算。

原生 router 在真正执行时仍可作为权威选择；预测器只指导搬运，漏预测专家精确补载，则保留原始路由语义。这里的语义保持不等于跨不同 kernel、归约顺序的逐位一致。

### 3.4 序列预测与 speculative lookahead

**信号：** 多层/多 token 激活序列，或轻量 draft 模型产生的未来表示和路由。

**流程：** 预测未来多个层或 decode step 的专家 → 形成更长的传输窗口 → 随真实结果更新预测与队列。

**代表：** MoE-Beyond、SP-MoE、MoE-SpeQ、MoE-SpAc、SPICE、SeqMoE。

这里需要区分：

- **专家序列预测：** 只预测专家使用，不直接生成可提交的 token。
- **speculative decoding 辅助预取：** draft 生成候选 token，再利用其路由预测 target 需求；必须计入验证、拒绝和额外专家集合。
- **draft hidden-state rollout：** 用轻量计算推进未来表示，以获得更深的专家预测，不应自动等同于标准 speculative decoding 的加速机制。

长窗口有利于慢速存储，但错误预测会占用更久的缓存。多步 rollout 训练需要处理自身预测带来的分布偏移。SeqMoE 采用序列预测和 scheduled sampling；SPICE 根据置信度和硬件需求决定 lookahead。

MoE-Beyond 的摘要报告约 97.5% accuracy、86.6% F1，并给出模拟缓存命中改善。稀疏多标签任务存在类别不均衡，因此 accuracy、F1、top-k recall 和真实端到端性能必须分别报告。

### 3.5 预取预算、截止时间与收益感知调度

这是与预测器正交的一条路线：即使预测集合相同，传输顺序也可能决定是否有收益。

**需要管理的状态：** resident、ready、inflight、queued、剩余字节、使用截止时间、带宽、可用缓存槽、是否可在 chunk 边界取消。

**典型决策：**

- 过滤已经驻留或正在加载的专家。
- 根据候选置信度、到位概率和避免的等待确定优先级。
- 限制超出可用窗口的预取，避免把需求传输排在无效预测之后。
- 真实路由到来时优先处理必要 miss，取消尚未发出的无效工作。
- 先计算已到位专家，利用这段时间继续搬运缺失专家。

**代表：** ProMoE 的分块搬运与 early preemption；HybriMoE 的 impact-driven prefetch；SpecPrefetch 的 profiling 预算；SeqMoE 的 deadline scheduling。

不能假设已启动的 CUDA copy 可随时中断。分块使队列更容易响应真实需求，但更多小传输也会增加启动开销。单纯提高预测 recall 可能反而降低 tokens/s。

### 3.6 预测驱动的缓存与全局内存分配

**目标：** 在有限驻留空间内减少未来必要加载，而不是只留最热门专家。

**典型方案：** 分层容量分配、层间共享池、带预测的下一次使用距离、未来使用概率与搬运成本联合评分。

**代表：** MoE-Infinity 的激活轨迹；AdapMoE 的 DP 缓存容量分配；FATE 的浅层偏置；HOBBIT 的多维缓存管理；SeqMoE 的 probabilistic Belady。

预测缓存不能偷看真实未来。真实未来已知的 Belady 适合做离线参照，其优化的是给定访问序列下的缓存 miss，不是包含预测、并发传输、质量变化的端到端时延最优解。

缓存必须保护仍在计算或等待消费的对象，并计入双缓冲、预取 staging、量化元数据、KV cache、预测器和补偿器占用。

### 3.7 改变路由时机或模型结构

**代表：** Pre-gated MoE。

将后续层的路由决策提前，使实际专家身份较早确定，从根本上减少“等 hidden state 才知道搬谁”的依赖。这与旁路预测器不同：它改变了模型计算/路由结构，通常需要训练或适配，不能视为任意原模型的透明 offloading 优化。

适合能参与训练、设计模型结构的项目；对本仓库这种以已有 checkpoint 为对象的剪枝研究，宜作为单独路线。

### 3.8 近似执行与 CPU/GPU 异构恢复

**核心：** 对无法按时到位的专家，不一定都走同步加载。

| 动作 | 代表 | 对输出的影响 |
|---|---|---|
| 减少本 token 激活专家 | AdapMoE | 改变计算，需质量评估 |
| 用已缓存相似专家替代 | BuddyMoE | 近似替换，需验证 token 条件下的误差 |
| 用已预取额外候选补足 | APEX stall-free 模式 | 改变原始专家集合 |
| 共享专家 + 低秩残差 | SPICE | 近似缺失专家输出，依赖模型结构 |
| 动态选择较低精度权重 | HOBBIT | 减少字节但引入量化误差 |
| CPU 执行原专家，仅传激活/结果 | Fiddler、HybriMoE；SPICE 的精确恢复分支 | 可保留专家计算语义，但受 CPU 算力与主存带宽约束 |

CPU 分支不是免费的：要比较 CPU 计算与激活往返成本，和原权重传输加 GPU 计算的完成时间。混合系统包含精确恢复分支，不代表其中近似分支也具备原模型等价性。

## 5. 对本课题最关键的近期与直接相关工作

### 5.1 AdapMoE：已经建立剪枝—预取—缓存的联系

原文用损失扰动和 Fisher 对 Hessian 的近似估计层敏感度，动态决定是否减少激活专家，重点研究 top-2 到 top-1 的选择。其预取不是独立猜原始 top-k：预测未来需求时已经纳入 adaptive gating。

下一层需求已在缓存时，它可以把预取视野推进到后续层；第一层还设计了利用上一 token 最后层激活的辅助预测。缓存部分以动态规划分配各层容量，降低建模的按需加载成本。

作者报告平均少激活 25% 专家、相对其基线约 1.35× 加速，在所测条件下未出现精度下降。这里的“未下降”是实验结论，不是任意数据和阈值下的无损保证。

因此，新方案至少应回答：相对 AdapMoE，是否增加了实时到位信息、关键路径代价、条件替换误差、高 top-k 子集选择，或更准确的端到端联合优化？

### 5.2 ProMoE：工程调度决定预测能否转化成收益

ProMoE 的重要性不只在预测器。它把预测和加载错开以扩大窗口，拆分专家矩阵传输，真实路由确定后尽早停止不再需要的排队任务，并优先执行已就绪专家。

其 GoodPred 指标同时关注预测与及时到位。论文相对手工优化缓存的 decode 收益与相对完整 offloading 框架的收益不同，不能把“最高加速”都归因于某一个 predictor。

对剪枝系统的启发：减少需求之后，必须及时修改待发送队列，否则仍可能把已经决定跳过的专家搬进来。

### 5.3 SpecPrefetch：候选越多不一定越快

SpecPrefetch 用低秩映射预测下一层路由分布，以冻结的原生 router 作蒸馏目标，并根据 profiling 得到的重叠窗口限制预取数量；驻留和 inflight 专家不重复加载。

它提供真实 Snapdragon 8 Elite / Adreno 825 平台实验，包含 4-bit DeepSeek-VL2-Tiny，文中单专家约 1.94 MB。冷 NVMe 条件的收益约 7–8%；约 20% 的较大收益对应模拟更慢 UFS 加载延迟的设置，不能写成所有实际手机存储条件下的收益。

它直接说明：优化目标应是“可用时间内值得搬的专家”，不是无限扩大候选集合以追求 recall。

### 5.4 APEX：置信度驱动预算与可用专家替换

APEX 在 attention 前预测，除基础 top-k 外，用学习式置信度模型决定额外候选数量。精确模式在真实路由后补齐 miss；stall-free 模式使用已到位原专家，并从额外预取候选中选择原 gate 评分较高者补足。

其性能/能耗结果来自综合校准的周期级协同仿真，包括 RTL 综合与存储建模；作者报告最高约 26% token 时延降低、41% EDP 改善。其硬件模型涉及片外 LPDDR5X 与片上 SRAM，不是本项目的 Flash→DRAM 加载路径。这里借鉴候选预算与近似执行机制，手机 Flash 收益需独立实测。

低 top-k 模型的近似容忍度可能更小；原文中 Phi 的质量损失比高 top-k 模型更明显。因此“已到位就替换”需要独立的质量控制。

### 5.5 BuddyMoE 与 SPICE：miss 处理已经进入模型近似

BuddyMoE 离线分析共激活与输出相似性，运行时寻找已缓存 buddy，结合 token 路由熵、CPU 驻留需求比例、覆盖阈值等条件决定替换。作者报告最高约 10% TPS 改善。共激活只是候选线索，不能在新模型上直接当作输出可替代性的证明。

SPICE 进一步使用轻量 draft 预测未来需求；对符合条件的缺失专家，以原生共享专家为基底加上低秩残差近似；重要剩余工作选择原权重加载或 CPU 执行。作者报告最高 3.12× TPOT 加速，包含预测、近似与异构执行的综合贡献。

本仓库的 Qwen3-MoE 路径没有可直接复用的原生 shared expert，不能照搬 SPICE 的共享基底假设。若额外构造基底，训练、常驻内存和计算代价都属于新增成本。

### 5.6 SeqMoE：预测、时间调度和运行时一起优化

2026-09-11 的预印本 SeqMoE 用 Mamba2 序列模型预测整段层级激活并跨自回归步展开。预取按带截止时间的任务调度建模；缓存用递归预测构造 probabilistic Belady；执行层使用全局专家槽位、映射与图兼容的管理机制。

论文摘要报告在 45% 专家驻留条件下平均 96.97% 命中率，达到 full-load 性能的 80.22%。具体模型配置并不完全一致，正文中存在不同驻留比例；这些数字不能直接移植到本仓库或手机。预测器本身也有计算与百 MB 量级内存成本，需要纳入公平比较。

对本课题而言，“使用截止时间调度”或“预测多个 token”已经有非常直接的先例。增量应落在**质量约束如何改变最终执行需求、补偿选择与关键路径**，而非只重新命名预取调度。

## 6. 如何正确比较这些方法

### 精确性分层

- **搬运优化层：** 不改目标模型路由和权重表示，漏预测时补载原专家；通常保持计算语义。
- **表示优化层：** 动态量化等改变数值表示，必须评估相应质量变化。
- **执行近似层：** 跳过专家、替换专家、低秩补偿或修改实际 router，必须评估模型质量。

含多个层次的完整系统应按分支说明，不能统一贴“无损预取”标签。

### 指标分层

| 指标 | 实际衡量内容 | 常见误读 |
|---|---|---|
| 多标签 accuracy / F1 | 预测标签质量 | 非激活标签很多时 accuracy 可偏高 |
| Recall@m / Precision@m | 给定候选预算的覆盖与浪费 | m 不同的结果不能直接比较 |
| Cache hit | 访问时已有专家 | 可能来自长期缓存，而非本次预测 |
| Deadline-ready recall | 真正使用前已经到位的比例 | 预测正确但来晚的专家仍会等待 |
| 每 token 必要/实际传输字节 | 数据移动负担 | 必须含错误预取与取消前已搬字节 |
| Demand stall | 真正暴露的加载等待 | 不等于所有 DMA 时长之和 |
| TPOT / TTFT / tokens/s | decode 延迟、首 token 延迟、吞吐 | 多 batch 吞吐加速不等于单请求 TPOT 加速 |
| 质量—延迟曲线 | 近似执行的实际取舍 | 固定平均 k 不代表固定质量 |

HOBBIT 的消融尤其值得注意：在其配置下，单独预取对 Mixtral decode 仅约 1.01×，对 Phi 甚至略降速；结合动态混合精度后，预取约带来 1.05×。其整体系统最高加速并不等于预取模块收益。

DuoServe-MoE 的 prefill 双缓冲、token 分组与 decode 预测一起贡献结果；Klotski 通过多 batch 获得更大重叠窗口。应把这些结果放回对应的 batch、阶段和内存预算中阅读。

## 7. 与本仓库的衔接

仓库已有动态 top-k / top-p、层预算、输出缩放和有向专家替换，适合研究**token 级激活选择如何降低实际权重需求**。它们比仅用全局频率删除专家，更贴近当前问题。

但已有 Python MoE block 保留完整专家张量；减少执行专家不自动形成真实 offloading。现有 trace 与 cache simulator 更适合研究访问集合和加载次数，尚不足以证明异步预取的端到端收益。

手机端推荐组合：

1. 低成本预测基线：FATE 式提前 gate；训练式比较：小型低秩 predictor，学习剪枝后的需求。
2. 激活选择：原有 top-p、敏感度/层阈值生成质量可行候选，再结合 DRAM 就绪与 Flash 读取完成时间选择。
3. 读取调度：对 Flash 请求去重、限额，按需读取优先；在单请求计算中隐藏必要读取。
4. 增强机制：复用 DRAM-ready 的可替代专家输出，并按真实缺失模式校准缩放。
5. 研究验证：同手机、同量化、同总 DRAM 和同质量下，分别比较实际 Flash 字节、暴露等待与 batch=1 TPOT。

方案细节、公式、仓库映射与实验矩阵见[配套算法设计](D:/华为/MoE-Compressors/docs/research/moe_prefetch_pruning_proposals.md)。

## 8. 范围边界与仍需验证的问题

- 部署范围为手机、Flash–DRAM–SRAM、batch=1；具体机型、模型、量化格式和执行后端仍需确定，读取服务时间和接口能力以目标设备测量为准。
- PopFetcher 等分布式 MoE 训练预取，以及专家并行 token/all-to-all 的提前调度，不作为单设备权重 offloading 的直接速度基线。
- 论文宣称的“首次”“最优”与“无损”不在这里作为已证明的一般结论；最优性通常依赖具体调度模型，质量通常来自有限任务评测。
- 最新预印本的接收状态、实现可用性、跨模型稳健性仍有不确定性；本报告以明确的方法与证据范围支持设计，不作可复现性保证。
- 预取和剪枝改变运行分布后，预测器、质量估计器与缓存策略都需要重新验证，尤其是长输出、代码/推理任务及任务切换。
